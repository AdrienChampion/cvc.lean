4. Terms🔗

Cvc.lean exposes two API-s for terms: Typed and Untyped. The former provides very strong static guarantees by strongly-typing terms; the latter does not but is more flexible, allowing in particular to build lists/arrays of terms of different sorts.

NB: cvc.lean enforces type-safety through definition irreducibility, which means you need to use Lean's module system to get any of its benefits.

Terms can be constructed by calling constructor-functions, but cvc.lean also provides a syntax extension smt! ... that supports Lean-like syntax to create terms. This discussion below presents both, but the rest of this document will almost always rely on the syntax extension.

4.1. Typed Terms🔗

🔗def
Cvc.Typed.Term [Ω] : Type → Type
Cvc.Typed.Term [Ω] : Type → Type

A cvc5 term whose sort is the one the Lean type α denotes.

Term Int, Term (Set Bool) and Term (Int → Bool) are terms of the SMT-LIB sorts Int, (Set Bool) and (-> Int Bool); a Lean type denotes a sort through its ToTyp instance. Every constructor states its sorts through the index, so a sort mistake is a Lean type error rather than a cvc5 error at runtime, and a value read out of a model comes back as an α.

The index is phantom: at runtime a Term α is exactly a Cvc.Untyped.Term. erase goes down for free, and Cvc.Untyped.Term.typeCheck goes up by checking the term's sort.

Typed terms have a type parameter for the actual Srt of that term. We saw previously that ToTyp links types to Srt-s, and it is precisely the mechanism used here. Typing terms lets us check statically that term constructors are invoked in a valid way, and makes their signature as precise as it can be.

Using the smt! extension:

open Typed in conj := (and b1 b2) i1_pos := (<= 0 i1) ite := (ite (<= 0 i1) i1 i2) #eval Env.runIO do let b1 ← Term.mkSymbol "b1" let b2 ← Term.mkSymbol "b2" let conj ← smt! b1 ∧ b2 println! "f_i_b : {← f_i_b.getSort} := {f_i_b}" -- alternatively let f_i_b' ← f.apply2 i b println! "f_i_b' : {← f_i_b'.getSort} := {f_i_b'}"

Using the smt! extension:

open Typed in f_i := (f i) f_i_b := (f i b) f_i_b' := (f i b) #eval Env.runIO do let f ← Term.mkSymbolAs (Int → Bool → Int) "f" let i ← Term.mkSymbol "i" let f_i ← smt! f i println! "f_i := {f_i}" let b ← Term.mkSymbol "b" let f_i_b ← smt! f_i b println! "f_i_b := {f_i_b}" let f_i_b' ← smt! f i b println! "f_i_b' := {f_i_b'}"

Of course, type-checking catches any invalid-sort mistake we make.

4.2. Untyped Terms🔗

🔗def
Cvc.Untyped.Term [Ω] : Type
Cvc.Untyped.Term [Ω] : Type

A sort-erased cvc5 term.

The term carries no sort on the Lean side: its sort is known to cvc5 alone, so a sort mistake, such as and applied to an integer, is reported by cvc5 at runtime. In exchange, terms of different sorts share one type, and an Array Term can hold them side by side.

A term belongs to the Ω scope it was built in and cannot leave it. At runtime it is exactly a cvc5 term, so the wrapper costs nothing. typeCheck checks its sort against a Lean type and gives it that type as an index, producing a Cvc.Typed.Term.

Untyped terms do not have a type parameter corresponding to their sort, which means untyped term constructors do not provide any static guarantee that the result is a valid term. Instead, invalid terms will fail at runtime.

Unlike the typed API, the sort of an untyped term for a function symbol cannot be inferred and must be given explicitly. The first way to do so is to pass the actual sort.

A symbol of the given sort: a fresh uninterpreted constant.

The second way is to pass the Lean type that we would use to create a typed term.

mkSymbol takes the sort itself; this names it by the Lean type denoting it.

4.4. Bound variables, lambdas, quantifiers🔗

Cvc.lean's typed API types bound variables just like it types terms.

🔗def
Cvc.Typed.BVar [Ω] (α : Type) : Type
Cvc.Typed.BVar [Ω] (α : Type) : Type

A bound variable.

It also provides a type for collections of BVar-s.

🔗def
Cvc.Typed.BVars [Ω] : Type 1
Cvc.Typed.BVars [Ω] : Type 1

A typed-list of BVars.

The untyped API for bound variables is very similar but with no type information. Cvc.Untyped.BVars is thus simply an array of untyped bound variables, and all checks are performed at runtime. We only present the typed API in this section.

As long as this list of bound variables (and their type) is known statically, functions such as Term.lambda are able to deconstruct it and infer the type of the corresponding function.
