    Function-application constructors, typed #

    A function's index is the curried arrow α → β → γ, which Typ.toSrt flattens into the SMT sort (-> α β γ). applyN takes an Args spine and so covers every arity; apply/apply2/apply3 are the fixed-arity spellings over it.

    They flatten, inheriting that from the sort-erased constructors: applying a term that is already an APPLY_UF appends to its children rather than nesting. So the CoeFun chain f a b c builds the same flat term applyN does, and stays clear of the function-sorted intermediates that would otherwise force a higher-order logic.

    Args φ β is the arguments that take a φ down to a β, and the spine you build is what says how many there are. done is an explicit base case, so nothing ever has to ask whether β is "still an arrow" — the question that makes drop-last on a right-nested index intractable.

    Stopping the spine early is a partial application, and it is sound: cvc5 accepts fewer arguments than the arity and gives the term the remaining function sort, which is exactly the β the spine computes.

                          Viewing an application #

                          Hand-written, since application flattens and its arity is arbitrary: Cvc.Spec.Fun only specifies applyHo, whose view View.Fun is generated. The arguments' sorts are whatever the function's domain is, which the application's sort does not fix, so they are a list of Typs from which the function's index is computed. Matching on the list refines both: .apply [.int, .bool] f (.cons x (.last b)) gives f : Term (Int → Bool → τ.Denote), x : Term Int and b : Term Bool.
